## 1. Problem, framed technically
Malicious APKs (fake hospital, courier, adult-content apps) read or forward SMS OTPs. When a bank detects something odd it **blocks**, which tips off the attacker and teaches the bank nothing about the mule accounts the money was meant for. The bank also cannot tell **which delivery channel leaked**: SMS forwarding malware, SIM swap, email compromise, or the user being socially engineered to read the code aloud.

## 2. The invention
1. **Per-channel codes.** For one authentication session the server derives distinct codes per delivery channel: `c_ch = Trunc(HMAC(k, session ‖ channel ‖ nonce))` for SMS, push, email and voice. Each is valid for the session, so the user experience is unchanged. The server keeps the code→channel map.
2. **Leak attribution.** When a code is submitted, the server identifies the channel it came from and combines this with device binding, network (ASN/IP), time-to-submit and input automation signals. *SMS code submitted from a device other than the bound device* is strong evidence of SMS-channel compromise. A code from a channel that was never shown to the user (a canary channel) proves interception outright.
3. **Honey-session diversion.** On a compromise event the session is not blocked but transparently served by a **honey environment**. It shows synthetic balances derived from the real ones (scaled and perturbed) and a **shadow ledger** in which transfers appear to succeed and no money moves. The attacker's beneficiary additions (mule accounts), device fingerprints, phishing-kit infrastructure and cash-out paths are harvested and pushed to mule-intelligence systems (in India, e.g. RBIH's MuleHunter.AI consortium).
4. **Protect and notify.** The real account is silently locked for outbound transfers, and the genuine customer is contacted through a verified channel (in-app, or a verified-number call).
5. **Speculative pre-evaluation.** While the user is still entering the code, the server speculatively evaluates risk for the pending transaction, including payee risk and device state, so honest users see no added latency. This is the Spexis-style parallel speculation.

### Technical effect / evidence
Channel-level compromise attribution accuracy. Mule accounts harvested per diverted session. The attacker's time-to-detection of the honey environment. Added latency for honest users (target: 0 ms p95).

## 4. Draft claims
**Claim 1.** A method comprising: generating, for an authentication session of an account, a plurality of distinct authentication codes each associated with a respective delivery channel; delivering the codes over the respective channels; receiving a submitted code and determining the delivery channel associated with it; determining a compromise of the delivery channel based on the determined channel and at least one of an identity of a submitting device and a device binding of the account; and in response, routing the session to a sandboxed environment that presents account data derived from the account and records requested transfers in a shadow ledger without movement of funds, while recording beneficiary identifiers entered in the session.
**Dependent:** a canary channel whose code is never displayed to the user · synthetic balances generated by a perturbation function · export of harvested beneficiary identifiers to an inter-bank mule registry · silent outbound lock plus verified-channel customer contact · speculative risk pre-evaluation in parallel with code entry · a time-to-submit automation feature.

## 5. Eligibility
Authentication-protocol and session-routing mechanics are technical in US, IN and EP terms. Avoid claiming "detect fraudsters and learn about mules" in the abstract.

## 6. Commercial path
Banks with high SMS-OTP dependence (India, SE Asia, LatAm), authentication vendors (OneSpan, Entrust), and core-banking digital channels.

## 7. PoC (4 weeks)
An OTP service with per-channel codes, a honey-environment mock with shadow-ledger APIs, and red-team simulation with SMS-forwarding malware.

## 8. Risks
Legal review of deception and of evidence use (India: IT Act and PMLA coordination with LEA). Honey-environment fidelity. Some users forward OTPs to family members, which is benign and needs an allow-list.
